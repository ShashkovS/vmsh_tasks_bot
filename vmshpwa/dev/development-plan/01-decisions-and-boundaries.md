# Принятые решения и границы продукта

Дата последней фиксации: 27 июля 2026 года. Документ объединяет все ответы владельца продукта, включая последний полный опросник, уточнения classroom planner и ответы на вопросы, возникшие при реализации. При расхождении с более ранними документами решения из этого файла имеют приоритет до синхронизации тематического документа.

## Первый рабочий выпуск

- Первый реальный запуск относится к сезону 2025–2026, занятиям 39, 40 и 41, сразу для всех трёх учебных уровней.
- Student должен позволять полностью провести онлайн-занятие без очного контура: прочитать материалы и новости, сдать все типы задач, задать вопрос, получить проверку и увидеть прогресс.
- Staff к запуску должен позволять загрузить материалы, заполнить названия и настройки задач, настроить подсказки и публикацию, запустить занятие, вести очередь и саму проверку, смотреть статистику.
- В первую версию Staff входит административное планирование очных аудиторий. Не входит отдельный интерфейс очного учителя для выставления результатов и печати комплектов.
- Опросы и игра в первую версию не переносятся. Остальные рабочие возможности Telegram должны сохраняться или иметь эквивалент в кабинетах.
- Старый сайт пока обновляется отдельными скриптами. Его публикация не входит в новый content pipeline первого выпуска.
- Печатный конвейер, быстрый очный интерфейс выставления плюсов, общий publisher публикаций из Staff в Telegram-каналы и настоящая AI-проверка относятся ко второй версии. Узкая персональная classroom delivery Student — отдельное v1-исключение.

## Каналы и постепенный переход

- Telegram и PWA работают поверх одной предметной модели. На старте можно начать решение в PWA и продолжить через Telegram либо наоборот.
- Уведомление об ответе или проверке по возможности приходит в тот канал, из которого была отправлена соответствующая работа или задан вопрос.
- Аннотация Staff для Telegram превращается в отдельный PNG, где слой разметки объединён с исходной фотографией; исходный WebP в хранилище не изменяется.
- Все еженедельные `_external_pipelines` продолжают работать до полного переезда. Замена выполняется по одному процессу с проверкой совместимости.
- Новости импортируются из Telegram начиная с 1 апреля 2026 года. Изменение или удаление исходного поста отражается в PWA; ручное скрытие в Staff влияет только на PWA.

## Учётные записи и сессии

- Student batch принимает заданный login и Telegram-token password вместе с
  ФИО, optional датой рождения и классом. Конфликт login получает предложенный
  случайный suffix `-NN`, видимый в preview. Legacy transliteration importer
  остаётся только compatibility/rehearsal path и не определяет target v1 UX.
- Test accounts с `qwerty*` разрешены для летнего MVP-прогона и затем удаляются.
- Учитель и родитель одного человека используют отдельные логины и отдельные audience sessions.
- Связь Family–Student является many-to-many: у ребёнка может быть несколько родительских аккаунтов, у родителя — несколько детей.
- Family batch хранит имя, заданные login/plaintext password, список email для
  будущих рассылок и список login детей. Student batch отдельно хранит ФИО,
  optional дату рождения/класс, заданные login и Telegram-token password.
  Credential mail в v1 отправляют внешние скрипты; обычные browser API и
  operational logs plaintext не раскрывают.
- Student, Family и Staff sessions истекают в ближайшее 10 августа. Все кабинеты используют отдельные cookie names и paths.
- В production нет mock auth. CSP, server authorization, nginx rate limiting, session revoke и device journal сохраняются как обязательные технические механизмы.
- Credential-like literals в старой migration `0038` не копируются в fixtures,
  отчёты или новый auth source. Владелец принял риск их присутствия в закрытой
  истории репозитория; отдельная чистка истории Git не входит в текущий план.

## Группы и права

- В каждом курсе у школьника одна активная группа, а `course_group_access` даёт доступ к дополнительным группам этого же курса: можно читать материалы, сдавать задачи и получать проверку. Legacy `allowed_groups` миграционно раскладывается по курсам.
- Смена активной группы немедленно меняет текущий набор задач. История результатов и уведомления по старым группам сохраняются.
- Для прошедшего занятия статистическая группа школьника определяется уровнем, на котором он показал лучший результат. Рассылка результата учитывает решённое по всем доступным уровням.
- Самостоятельную смену online/in-person не блокирует крайний срок. Изменение остаётся явным, подтверждаемым и записывается в историю.
- Обычный учитель может менять уровень ученика и перепроверять работу. Он не загружает условия и не меняет правильные ответы или checker.
- Учителю недоступны рассылки, аудитории и аудит. Статистика кружка ему доступна; объектные операции всё равно ограничиваются серверными правами.
- Родитель может менять уровень и режим посещения связанного ребёнка.

## LaTeX и идентичность задач

- В source нет обязательного стабильного идентификатора задачи, и добавлять такую команду не требуется.
- Базовое сопоставление задач, условий и решений выполняется по порядку, как в `_external_pipelines/a12_dum_tex_files.py` и `a16_html_from_tex.py`.
- Если структура новой загрузки отличается от уже существующего занятия, Staff показывает отдельный интерфейс сопоставления: оставить прежнюю задачу, связать с новым элементом, вставить, удалить или подтвердить новую задачу. До разрешения неоднозначности публикация блокируется.
- Поддерживаемый язык — конструкции KaTeX плюс исторический набор `a16_html_from_tex.py`; `_vmsh_examples` и три полных листка одного уровня служат регрессионным корпусом.
- LaTeX в Staff не редактируется. Сравнение revisions полезно, но не обязательно для первого выпуска.
- Условие можно исправить после начала сдач. Школьник, видевший предыдущую версию, получает заметный индикатор обновления; teacher review всегда показывает последнюю опубликованную версию.
- Публикацию условий, подсказок и решений можно планировать по времени. Новая публикация сразу заменяет видимую версию. Скрытое после публикации занятие выглядит для ученика так, будто его нет.
- Операционные документы различают воскресный cutoff приёма (сейчас 13:00) и более позднюю публикацию решений (14:00/15:00). Поэтому модель хранит отдельное `submission_closes_at`; фактический `solution.published_at` является событием публикации, но не вычисляет дедлайн задним числом. По закрытому `SCHEDULE-01` перенос решения не двигает cutoff: он меняется только отдельным подтверждённым действием.
- Темы являются необязательными тегами: их можно назначить после импорта или загрузить пакетно таблицей.
- Обязательные редактируемые метаданные: название, тип задачи, тип ответа, сообщение об ошибке формата, сообщение о неправильном ответе, поздравление и теги тем.
- Кандидата synonym-group по одинаковому названию подтверждает администратор после загрузки.
- Условия, решения и подсказки остаются LaTeX-источниками; Web/Telegram/SVG/WebP/PDF — производные. Печатный интерфейс откладывается во вторую версию.

## Тестовые задачи

- Сохраняются все исторические типы и форматы ответов. Улучшения допустимы только как совместимое расширение.
- Ответ, который не прошёл разбор формата, не расходует попытку. Все введённые ответы сохраняются в истории.
- После правильного ответа можно отправлять новые ответы.
- Ошибочный автоматический verdict исправляется admin-перепроверкой по существующей логике `problem_recheck`.
- Набор проверочных примеров для `cor_ans_checker` желателен, но не блокирует публикацию. Ответ для ещё не настроенного checker принимается со статусом «ожидает проверки», а после настройки запускается пакетная перепроверка.
- Offline-ответ, созданный до `submission_closes_at`, обрабатывается как своевременный даже при более поздней доставке. Расхождение часов больше одного часа помечается как подозрительное для диагностики, но не теряет саму отправку.

## Письменная сдача

- Текст и выбранные фотографии образуют одну логическую отправку. В Telegram она может состоять из нескольких сообщений и media group, но adapter связывает их с одной записью.
- Разрешена отправка только текста. LaTeX-текст сохраняется как введён, но в первой версии не рендерится в discussion composer/viewer.
- Работа становится видимой учителю только после успешной загрузки всех входящих в неё фотографий. Неудавшийся файл повторяется отдельно, а логическая отправка остаётся незавершённой.
- До начала первой проверки ученик может с подтверждением изменить текст или удалить исходную отправку. После начала проверки он не меняет её задним числом, но может дослать новый материал в тот же тред.
- Материал, досланный во время проверки, должен попасть в текущую проверку. Завершение review поэтому проверяет актуальную версию треда и при гонке заставляет reviewer обновить evidence перед сохранением.
- В Student полезны отдельные действия «дописать ответ» и «пересдать решение», но для backend и teacher queue это один тип добавления материала.
- Поздняя письменная работа попадает в обычную очередь. В нормальном потоке сдача после дедлайна запрещена; более поздняя доставка offline-очереди не считается поздней.
- Telegram и PWA показывают один хронологический тред.
- Фото уменьшаются до 1920 px, сохраняются как WebP, максимум 10; originals не хранятся. После завершённой проверки зафиксированные изображения нельзя изменить или удалить.
- Owner-confirmed core исправления ошибочной задачи: teacher переносит одно или
  несколько выбранных сообщений/фотографий, а Student видит их в целевой
  истории. Implementation default добавляет admin, обязательный preview и
  возможность исправления после review; append-only invariant не позволяет
  переписывать bytes/IDs, review evidence или прежний verdict.

## Проверка, реакции и аннотации

- Comment формально необязателен при любом verdict. Для любого результата, кроме «Зачтено», Staff просит подтвердить сохранение без комментария.
- На одну проверку teacher выбирает не более одной скрытой реакции из существующего registry БД. Student также выбирает не более одной реакции соответствующего типа.
- Teacher и student могут изменить или удалить свою реакцию в течение одного часа после её установки.
- Отдельных workflow-статусов для спорной проверки пока нет. Admin видит реакцию, может перепроверить работу и заменяет текущий verdict согласно существующей логике `results`.
- Учитель может исправить собственный ошибочный verdict. Обычное teacher-сообщение внутри треда без verdict не поддерживается.
- Owner-confirmed annotation v1: карандаш, ластик, текст, стрелка,
  прямоугольник и поворот изображения. Zoom/pan — локальное состояние
  просмотрщика и не сохраняется вместе с normalized overlay. Highlight и
  компактная палитра примерно из 4–5 цветов — необязательная implementation
  detail; после отправки annotation в любом случае не редактируется.
- Незавершённые comment/annotation drafts учителя хранятся локально и восстанавливаются после потери связи. Причина отказа от проверки не сохраняется.
- Повторная сдача после доработки не получает специального приоритета.
- Review queue сохраняет атомарную 30-минутную аренду и текущий выбор случайной работы из первых восьми старейших кандидатов.

## Вопросы и SOS

- Вопросы приватны: teachers видят все доступные им вопросы, ученик — только свои.
- SOS — обычный вопрос человеку, связанный с задачей или с занятием в целом; отдельный graded verdict для него не нужен.
- Вопрос не закрепляется за одним teacher. Это диалоговая лента в рамках задачи либо отдельная лента занятия для общих вопросов.
- Продолжение одного вопроса между Telegram и PWA желательно, но не блокирует первый выпуск.

## Устные и очные занятия

- У группы может быть несколько устных окон; в текущем процессе их три. Создаёт и меняет их только admin. Поддерживается Zoom, другие providers не нужны.
- Устную задачу можно письменно отправить в обычную очередь письменных работ.
- Staff oral flow: найти школьника, увидеть уже зачтённое и быстро поставить или исправить плюсы; подробности наследуются из `docs/user_stories`.
- Аудитории разделены на три сущности: постоянный глобальный каталог, наследуемая между занятиями подтверждённая схема «аудитория → группа» и версионируемый план распределения очных школьников для конкретного занятия.
- Имя аудитории — непустая строка после trim. Внутренние пробелы сохраняются, уникальность проверяется по Unicode NFKC + casefold. Hard delete отсутствует: комнату можно скрыть и восстановить; глобальное переименование сохраняется в audit.
- В одной версии схемы аудитория относится максимум к одной группе, а группа может занимать сколько угодно аудиторий. Вместимость и веса не задаются; типичные 6/5/2 — только фактическое количество комнат по группам.
- Новое занятие напрямую использует последнюю подтверждённую схему. Первая правка материализует собственный draft, действующий с выбранного занятия. Изменение схемы делает уже рассчитанный план `stale` и требует preview, пересчёта и нового подтверждения.
- Распределение сначала сохраняет последнюю историческую допустимую аудиторию школьника для текущей группы, затем выбирает наименее заполненную аудиторию группы; равенство разрешает серверная естественная сортировка названий. Ручное перемещение выполняется компактным select без drag-and-drop; выбранные строки можно перенести массово одним общим select.
- Смена группы и online→очно сразу запускают то же правило для школьника. Переход очно→online снимает назначение. Если допустимой комнаты нет, школьник получает `reassigning`, а Staff — блокирующий инцидент.
- Выбор комнаты другой группы требует явного подтверждения одновременной смены группы школьника. Подтверждённые планы образуют доступную из строки школьника историю аудиторий; отдельная mutable history-таблица не создаётся.
- Classroom layout показывает цветовые маркеры групп и пары `очно/распределено`. Student plan состоит из компактных flex-wrap-карточек аудиторий и отдельной секции неназначенных; строки всегда отсортированы по фамилии и имени.
- В строке школьника видны nullable возраст на сегодня с одним десятичным знаком, класс и автоматически вычисляемая сила 0–10. В заголовке комнаты — count и средние возраст/класс/сила без неизвестных значений; каждое среднее округляется до одного знака. Сила обновляется несколько раз в день по адаптеру к `_external_pipelines/a53_calc_rating_new.py` и вручную не редактируется.
- Поиск по ученикам нормализует регистр, `ё/е`, пробелы и порядок имени/фамилии, допускает небольшие опечатки, подсвечивает найденную строку и позволяет перейти к ней.
- Правки распределения накапливаются локально, сохраняются между reload в account/lesson/version-scoped draft и отправляются на сервер только явным batch-save/confirm. Автосохранение каждой смены select на сервер запрещено.
- Скрытие используемой аудитории немедленно сбрасывает текущие назначения в «Аудитория переназначается», не меняет прошлые занятия и не откатывается автоматически при восстановлении комнаты.
- Подтверждение запрещено при смешении групп, несовпадении группы школьника с комнатой или наличии очного школьника без аудитории. Неиспользованные активные комнаты допустимы.
- Назначенную аудиторию видят Student и Family сразу после подтверждения нового плана через owner-scoped API/WS invalidation. Это обновление состояния само по себе не создаёт notification delivery.
- После подтверждения плана admin отдельным действием «Разослать аудитории» открывает recipient preview и выбирает PWA и/или Telegram. PWA создаёт персональные in-app/push сообщения только Student; Telegram отправляет личное сообщение каждому школьнику через существующего бота по server-side mapping. Family видит актуальное состояние, но не получает classroom push или Telegram delivery.
- Изменение назначения после рассылки помечается как `not announced` относительно последнего delivery batch. Автоматической повторной отправки нет: новый preview и send запускает admin явно. Draft и неподтверждённый план никогда не рассылаются.
- Первый перенос использует одноразовый dry-run/import текущего Excel-export с колонками `IDd`, `Уровень`, `Аудитория`; постоянный spreadsheet workflow не добавляется.
- Печать списков на двери, кондуитов и комплектов, а также быстрый очный ввод плюсов переносятся в отдельный Staff-раздел второй версии и сверяются с `a11`–`a14`.
- Первая версия не обещает compatibility export в `a11`–`a14`: legacy-печать остаётся отдельным операционным путём до собственного cutover. Узкая персональная рассылка аудиторий из Staff не превращает v1 в общий broadcast/print workflow.

## Новости и уведомления

- Telegram history импортируется с 1 апреля 2026 года. Telegram edit обновляет PWA, delete удаляет пост из обычной PWA-ленты.
- Staff hide действует только в PWA. Отправка созданной в Staff произвольной публикации в Telegram-канал относится ко второй версии; персональная classroom delivery описана отдельным типизированным workflow.
- Локальные публикации и баннеры создаёт admin. Полноценные личные/групповые рассылки переходят во вторую фазу вместе с Markdown editor и delivery workflow.
- Существующая специальная административная группа может стать целью рассылки во второй фазе; реальных исторических рассылок такого типа пока не было.
- Публикации и баннеры можно планировать. Баннер скрывается по окончании окна, обычная публикация сохраняется в ленте. Закрытие баннера хранится локально на конкретном устройстве.
- Неподдерживаемое Telegram-вложение игнорируется с диагностикой; нормальный импорт не должен регулярно создавать такие случаи.
- Owner-confirmed delivery view показывает per-channel counts и допускает
  частичный успех с раскрываемыми privacy-safe списками. Implementation default
  трактует «Повторить ошибки» как явную новую попытку только failed
  recipient/channel pairs и не дублирует уже успешные сообщения.
- Quiet hours 21:00–09:00 считаются в timezone пользователя и подавляют только звук.
- Review notifications всех задач одного ученика объединяются в одну пачку за 30 минут.
- На lock screen допустимо показать полную информацию о проверке. Уведомление считается просмотренным после не менее трёх секунд видимости соответствующего события.
- Read-state принадлежит account/event и синхронизируется между устройствами: любой PWA-клиент после непрерывных трёх секунд видимости идемпотентно подтверждает событие серверу. Telegram delivery сам по себе не считается прочтением, потому что Telegram не даёт надёжного read receipt; открытие того же события в PWA снимает badge на всех устройствах после refetch/invalidation.
- Badge «Задачи» показывает число обновлённых/проверенных задач, уведомления по которым школьник ещё не видел.
- Family по умолчанию получает один недельный итог после окончания всей проверки занятия, а не поток отдельных проверок.

## Family

- Родитель видит фотографии, тред, comments, annotations и историю verdict ребёнка. Для простоты он получает тот же student-visible AI feedback и реакции ребёнка; скрытые teacher reactions ему не передаются.
- Родитель может независимо раскрыть опубликованную подсказку/решение и может менять уровень и режим посещения ребёнка.
- Отдельной семейной self-check операции нет, и она не влияет на прогресс.
- Session заканчивается 10 августа. В первой версии UI показывает только текущий сезон; данные старых сезонов остаются в БД для будущей истории.
- Для нескольких детей общие новости дедуплицируются, а групповые элементы получают подпись ребёнка/группы; точный визуальный вариант выбирается в Family stories без изменения API-смысла.
- Family не показывает сравнение ребёнка с группой.

## Сохранность незавершённой работы

- Reload, закрытие вкладки, PWA update и краткий обрыв сети не должны терять значимое незавершённое действие Student/Staff.
- Сериализуемые text/UI drafts сохраняются в `localStorage` после каждого осмысленного изменения; фотографии, blobs и outbox — в Dexie/IndexedDB. Draft namespaced по runtime, audience, account, entity и base version.
- Черновик очищается только после server receipt/confirm либо явного discard. При несовпадении base version показывается восстановление/конфликт, а не молчаливое last-write-wins. Session secrets в Web Storage не хранятся.
- Owner-confirmed core разрешает после прежнего входа cold start без сети и
  logout с непустым outbox после предупреждения. Implementation default
  показывает account-scoped cache/drafts без credential как
  `offline-unverified` не дольше известного `sessionExpiresAt`, проверяет server
  session до синхронизации и после подтверждённого logout/account switch очищает
  данные аккаунта, чтобы их не увидел следующий пользователь общего устройства.

## Прогресс и достижения

- Задача считается зачтённой при `VERDICT_TO_NUM >= 0.9`; остальные результаты не входят в счётчик зачтённых, хотя их веса могут использоваться во внутренних графиках.
- Denominator «из N» — число отдельных задач/подпунктов, а не число названий или карточек synonym-group.
- Поздние offline-доставки не отделяются в статистике, потому что после `submission_closes_at` обычная новая сдача запрещена.
- Violin показывает распределение числа решённых задач по занятию и повторяет текущую методику `web/trash_print_stats.py`/`trash_print_results.py` и `_external_pipelines/a54_upd_report.py`.
- Ни один Student/Family график распределения не отмечает самого ребёнка и не сообщает его позицию относительно группы. Эти данные можно при желании сопоставить самостоятельно, но интерфейс этого не делает.
- Для прошлого занятия школьник относится к уровню, где достиг лучшего результата; миграция сверяется с `temp_student_visits` и `_external_pipelines/a53_calc_rating_new.py`.
- Личная кривая «простые/сложные задачи» не выводится на лету только из `results`: отдельный версионированный analytics job воспроизводит `a53_calc_rating_new.py`, сохраняет persistent lesson snapshots и обновляет latest `student_strength` projection. Временные `temp_*` таблицы внешнего скрипта не становятся runtime contract.
- Распределение группы показывается только при размере выборки не меньше 30.
- В календаре один problem/item даёт не более одной активности за день независимо от числа его посылок.
- Streak считается неделями подряд с хотя бы 1, 2, 3 или 4 активными днями.
- Первые achievements: первая отправка задачи, первая письменная отправка, первое завершённое занятие, занятие с результатом не ниже максимума и streak milestones. Они начисляются и по существующей истории.

## Администрирование и Google

- Пользователи пакетно загружаются из Excel. Для школьника обязательны фамилия, имя, уникальный token/password, дата рождения и класс.
- Ошибочные строки пропускаются; после обработки admin получает отчёт о незагруженных строках. Повторный импорт сопоставляет пользователя по уникальному token.
- Admin может изменить любое поле пользователя, кроме `id`, заблокировать и архивировать его. Полное удаление не поддерживается.
- Выгрузка пользователей обратно в файл в первой версии не нужна.
- Первой заменяется загрузка task settings из листов «Задачи» и «Старые» файла `_external_pipelines/ВМШ 2025-26, информация для бота ВМШ — prod.xlsx`.
- Surveys пока не переносятся. Письма добавляются во второй или третьей версии.
- Обязательный минимум аудита: каждый новый login в совместимости с `signons`, смена группы и режима посещения в совместимости с `user_changes_log`. Content revisions и review history сохраняют собственную provenance/history.
- Backfill `user_changes_log` схлопывает последовательные повторные `G`/`O` с
  тем же значением: они были следствием повторного вызова legacy-команды, а не
  реальным переходом состояния.
- Legacy `written_tasks_discussions` импортируется одной непрерывной
  хронологией без выдуманной связи сообщений с конкретными review rounds; если
  точную связь нельзя доказать, её не восстанавливают эвристикой.
- При новом сезоне автоматически переносятся преподаватели; остальные данные создаются/импортируются заново.

## Эксплуатация и тестирование

- Production hostname пока не принят; целевые пути остаются `/student`,
  `/family`, `/staff`. Production и optional staging должны получить разные
  явно утверждённые lowercase FQDN через обязательный `@@PUBLIC_HOST@@` nginx
  template, без предположения на основе legacy-сайта.
- Краткое maintenance window для SQLite migrations допустимо.
- Миграции запускаются отдельным шагом maintenance window; application workers только сверяют schema version и не вызывают yoyo apply при обычном startup.
- Текущий cron сохраняет SQLite на другом физическом сервере и держит длинную
  историю. Запуск Telegram-модуля обработки новых сообщений из таких копий уже
  работал, но это не считается полной репетицией восстановления всех PWA
  данных; перед rollout нужен отдельный restore rehearsal.
- Отдельный backup всего S3 не требуется. Student images не versioned; teacher-authored отправленные artifacts должны оставаться восстанавливаемыми/immutable на уровне приложения или выделенного storage policy.
- Серьёзные сбои сообщаются в специальную служебную Telegram-группу.
- Новые возможности включаются сразу для всех трёх уровней, не поэтапно по группам.
- Migration/performance tests используют только согласованную изолированную
  копию `db/vmsh.db` вместе с WAL/SHM при их наличии. Source не изменяется:
  сначала создаётся copy/snapshot, затем в копии Faker заменяет все имена и
  фамилии, и только после этого запускаются migrations/load tests.
- Для opt-in Telegram integration есть test bot `@vmsh179devbot`; token читается только из test credential config. Владелец подтвердил canonical Bot API `chat.id = -1003913815635` приватного `vmsh179devbot channel`; это pinned test-only значение, а не вывод из UI ID. Бот добавлен admin. Live profile может публиковать, редактировать и удалять там synthetic/test payloads в пределах Telegram limits; unit/E2E от канала не зависят. Read-only bind проверяет canonical ID, private channel и bot capability и сохраняет immutable identity в owner-only local SQLite; write-smoke принимает destination только оттуда. Phase 2 переносит принятый binding contract в целевую course/group таблицу.
- Для content visual regression обязательно сравниваются PWA, Telegram и PDF для трёх листков одного уровня из `_vmsh_examples`.

## Принято 26 июля: многокурсовая модель

- Иерархия: `season → course → group → course_lesson/group_lesson`.
- У ученика несколько `course_enrollment`; active group и attendance mode независимы в каждом курсе.
- Group content/schedule/Telegram settings независимы; course даёт шаблоны и defaults.
- Синонимы действуют только внутри course lesson и объединяют данные логически, без переноса concrete IDs.
- Общая student chronology не имеет фильтра веток; teacher review объединяет
  посылки, но verdict принадлежит задаче последней по серверному времени
  приёма посылки. При равном времени internal submission ID служит только
  детерминированным tie-break; client time не участвует.
- Статистика раздельна по курсам; Student/Family не сравниваются с группой.
- Очное событие объединяет выбранные group lessons разных курсов и наследует прежний полный план групп.
- Authoritative модель: [`docs/courses-groups-and-lessons.md`](../../docs/courses-groups-and-lessons.md); раскладка по фазам: [`19-multi-course-delivery.md`](19-multi-course-delivery.md).
