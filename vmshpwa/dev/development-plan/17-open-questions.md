## Решения по вопросам внешнего ревью — 27 июля 2026

Все четыре развилки закрыты владельцем продукта. Они больше не блокируют готовность этапов.

### `SCHEDULE-01` — закрыт

`submission_closes_at` и публикация решения — независимые процессы. Перенос `solution_scheduled_at` не меняет cutoff. Дедлайн изменяется только отдельным явно подтверждённым действием с audit и уведомлением затронутых учеников.

### `AUTH-01` — закрыт

У всех настоящих школьников ожидаются корректная фамилия и пригодный Telegram-токен. Некорректные строки относятся к тестовым аккаунтам и не активируются как production Student web accounts. Phase 0 всё равно подтверждает это агрегированным preflight-отчётом; неизвестная строка не угадывается и попадает в явный список исключений без раскрытия токена.

### `CLASSROOM-01` — закрыт

Печать переносится отдельным Staff-разделом во вторую версию; v1 не обещает compatibility export в `a11`–`a14`. Рассылка аудиторий переносится в Staff уже в v1 как узкое admin-only действие, а не как общий broadcast composer. После подтверждения плана admin отдельно открывает preview, выбирает PWA и/или Telegram и нажимает «Разослать аудитории». PWA создаёт персональные in-app/push delivery только Student; Telegram отправляет каждому школьнику личное сообщение через существующего бота по server-side recipient mapping. Токены и chat IDs не попадают в browser payload.

Изменение подтверждённого плана обновляет Student/Family read model, но не рассылается автоматически. Admin видит число назначений, изменившихся после последней отправки, и запускает новый delivery batch явно. Family видит актуальную аудиторию через API/WS, но не получает classroom push или Telegram-сообщение.

### `RETENTION-01` — закрыт

Автоматического срока удаления и плановой очистки нет. За решение о ручной очистке отвечают администраторы. Она выполняется только управляемой manifest-driven операцией с preview/audit и согласованным обновлением SQLite/S3; произвольное удаление объектов из bucket не считается продуктовым workflow. До отдельного будущего решения данные хранятся бессрочно.

## Замечания ревью, не требующие продуктового ответа

- SQLite concurrency, `busy_timeout`, отсутствие `await` внутри transaction и deploy-only migrations оформлены как обязательный ADR/гейт этапа 0.
- `docs/db_structure.sql` больше не назван самостоятельным источником истины; authoritative schema восстанавливается из migrations и проверенного inventory. При этом замечание ревью об отсутствии `results` было фактически неверным: таблица в snapshot есть; проблема именно в возможном drift (например, `groups`).
- Правило досылки не менялось: всё submitted до commit текущей проверки входит в evidence. Фраза «более поздний entry» уточнена как «созданный после commit», а не «после начала review».
- Reaction actor выводится из типа реакции и связанного result/Zoom record; ambiguity/duplicates обрабатываются dry-run/quarantine, а не угадываются.
- Графики силы и лучший уровень явно переведены на versioned analytics snapshots по `a53`/`a54`, а не объявлены простым SQL над `results`.
- История занятий 1–38, queue `teacher_id` affinity, read-state между устройствами и численный load profile добавлены в соответствующие backfill/test gates.

Несколько тем сознательно перенесены во вторую или последующую версию и не должны незаметно попасть в первую:

- печатный раздел Staff и генерация комплектов по аудиториям;
- быстрый интерфейс очного учителя для внесения плюсов;
- публикация из Staff непосредственно в Telegram-канал;
- письма из Staff;
- опросы и игра;
- история нескольких сезонов в Student/Family;
- реальная AI-проверка;
- новый способ обновления старого публичного сайта.

Неблокирующие детали реализации перечислены в конце `01-decisions-and-boundaries.md`. Если в ходе разработки появится новая продуктовая развилка, она добавляется сюда отдельным датированным разделом, а после ответа переносится в соответствующий тематический документ. После ответа на вопрос здесь остаётся дата, выбранный вариант и ссылки на изменённые model/API/phase документы.

## Решения 26 июля 2026 года

По многокурсовой модели открытых продуктовых вопросов не осталось. Приняты независимые группы/расписания/Telegram bindings, per-course enrollment и статистика, логические синонимы с общей хронологией и combined review, а также `in_person_event` с полным наследованием прошлого плана выбранных групп. Решения разнесены в [`docs/courses-groups-and-lessons.md`](../../docs/courses-groups-and-lessons.md), model/API docs и [сквозной план](19-multi-course-delivery.md). Backend/migration implementation не считается выполненной.
