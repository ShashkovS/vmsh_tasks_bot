# Вопросы, возникшие при реализации

Этот файл хранит датированный журнал реальных продуктовых развилок, обнаруженных во время разработки. Он не заменяет закрытый исходный опросник в `17-open-questions.md`: новый вопрос появляется здесь только до получения решения, а принятый ответ сразу разносится по модели, API, этапам, UX и проверкам.

Статус на 3 августа 2026 года: все вопросы 1–19 получили решение и разнесены по
документам-владельцам. У пункта 10 отдельно остаётся недостающий operational
proof полного восстановления, но продуктовой развилки в нём больше нет.

## Проверка письменных решений

1. Должен ли преподаватель или администратор уметь исправить работу, которую школьник по ошибке приложил к другой задаче? Если да, переносится одна выбранная фотография или вся посылка; допустимо ли исправление после блокировки материалов завершённой проверкой; кто имеет это право; какие исходная и новая привязки остаются в журнале изменений и как исправление отображается школьнику в истории?

**Решено 27 июля 2026 года. Owner-confirmed core:** teacher может выбрать одно
либо несколько сообщений/фотографий, исправить выбранную задачу, а Student видит
материал в истории целевой задачи. **Безопасный implementation default:** то же
действие доступно admin с доступом к обеим задачам, начинается с preview и
разрешено в том числе после завершённой проверки. Коррекция остаётся append-only:
исходные bytes, IDs, problem association, immutable review evidence и уже
записанный verdict не переписываются и не копируются. Она хранит actor,
source/target, выбранные items, server time, request ID и причину; Student видит
пометку «Перенесено преподавателем», а исходная цепочка остаётся в Staff
provenance/audit. Если целевой задаче нужен verdict, он создаётся отдельной
проверкой. Этот default не является открытым продуктовым блокером.

### Объединённая проверка синонимичных задач

2. Если в одном объединённом кейсе есть несколько посылок в разные синонимичные задачи, какую из них считать последней для записи вердикта: последнюю по времени приёма сервером, по клиентскому времени создания или по другому правилу? Как разрешать совпадение времени?

**Решено 27 июля 2026 года.** Verdict и ответ записываются в concrete problem
посылки с максимальным server receive time. Если server timestamps совпали,
используется больший внутренний submission ID как стабильный технический
tie-break. Client time на выбор target не влияет.

### Инструменты аннотации

3. Какие инструменты должны войти в первую версию разметки фотографии: только карандаш, ластик, поворот и масштаб или также текст, стрелки, выделение и прямоугольники? Должны ли масштаб и положение холста сохраняться вместе с учительской аннотацией либо оставаться локальным состоянием просмотрщика?

**Решено 27 июля 2026 года. Owner-confirmed core:** первая версия поддерживает
карандаш, ластик, текст, стрелку, прямоугольник и поворот; масштаб и положение
холста остаются только локальным viewer state, не входят в annotation payload и
не меняют нормализованные координаты пометок. **Необязательная implementation
detail:** renderer и versioned payload могут также поддержать выделение и
компактную палитру примерно из 4–5 цветов. Точный набор палитры и наличие
отдельного highlight-tool не блокируют первую версию.

## Исторические данные доступа

4. В миграции `0038` обнаружены похожие на действующие данные доступа, которые нельзя переносить в fixtures, отчёты или новый web-вход. Остались ли они действующими и можем ли мы перед запуском web-аутентификации удалить их из актуального дерева репозитория и выполнить ротацию? Отдельно понадобится решить, требуется ли чистка истории Git или достаточно ротации и последующей migration без секретов.

**Решено 27 июля 2026 года.** Исторические значения в `0038` игнорируются как источник web-доступа и не переносятся в fixtures, отчёты или `auth_accounts`. Очистка истории Git и отдельная ротация только из-за этой migration не входят в текущий этап. Это не разрешает печатать или повторно использовать значения из migration: активация PWA опирается на контролируемый импорт текущих данных, а новые migrations не содержат credential rows.

5. Старый classroom pipeline передаёт `users.token` как `IDd`, а затем использует `IDd` при создании штрихкода на печатных кондуитах. Можно ли из этого штрихкода восстановить тот же Telegram-токен, который станет паролем PWA, и раздавались или сохранялись ли такие листы? Если да, перед web-входом нужно считать соответствующие токены раскрытыми и ротировать их; новый print pipeline в любом случае будет использовать отдельный несекретный public ID.

**Решено 27 июля 2026 года.** `IDd` и штрихкод содержат legacy numeric `users.id`, а не Telegram-токен. Сам внутренний ID не считается credential и не требует ротации Student token. Текущий print/barcode workflow пока не переносится; browser API всё равно использует отдельные opaque public IDs и не раскрывает способ чтения токена из БД.

## Журналы событий

6. В отслеживаемых Git файлах `logs/selected.jsonl` и `logs/cnt.py` есть настоящие идентификаторы, а во втором также имена, использованные при отборе событий. Можно ли оставить эти файлы и их историю в закрытом репозитории или их нужно обезличить и удалить исходные версии из истории Git?

**Решено 27 июля 2026 года.** Файлы и их история пока остаются в закрытом репозитории. Это не меняет правила производных артефактов: реальные строки, имена и идентификаторы не копируются в docs, fixtures, snapshots или отчёты; для тестов создаются синтетические данные по наблюдаемой структуре.

## Внешний недельный pipeline

### Где находятся отсутствующие зависимости?

7. Где лежат актуальные `z_CONSTS.py`, `z_helpers.py`, `z_cpdf.py`, модуль `plus_reader`, папка `tex_templates` и используемый скрипт почтовой рассылки, от которых зависят файлы в `_external_pipelines`?

**Решено для текущего объёма 27 июля 2026 года.** Reference-копии `z_CONSTS.py`, `z_helpers.py`, `z_cpdf.py`, `mega_floor_lists.tex`, `per_aud_lists.tex` и `prev_conduit_template.tex` добавлены в `_external_pipelines`. Они остаются characterization input, а не production-package. `plus_reader` сейчас не нужен: OCR кондуитов отложен после первой версии. Полное рабочее дерево `tex_templates`, рабочие Dropbox roots и внешний mail sender остаются явно зарегистрированными зависимостями соответствующих legacy/post-v1 процессов и не подменяются выдуманными fixtures.

### Можно ли подготовить обезличенный комплект?

8. Можно ли передать обезличенный тестовый комплект этих зависимостей без паролей, ключей доступа и данных школьников, чтобы сравнивать старый и новый pipeline на одинаковом входе?

**Решено 27 июля 2026 года.** Для локальной characterization разрешено использовать только изолированную временную копию `db/vmsh.db`. Исходную БД запрещено изменять. До получения любых тестовых производных в копии все имена и фамилии `users` заменяются значениями Faker; сама копия не коммитится. Credential/contact/content-bearing поля не переходят в committed fixtures: из обезличенной копии выводятся только минимальные синтетические fixtures и агрегированные доказательства.

### Какие скрипты используются сейчас?

9. Какие имена скриптов реально запускаются сейчас для PDF результатов предыдущего занятия, почтовых рассылок и разметки статистики на старом сайте? В описании процесса названы `a15_print_per_aud_conds_html.py`, `a21_create_mails.py` и `a22_mark_compl_in_html_new.py`, а в переданном snapshot соответствующие функции находятся в `a13_print_per_aud_conds_tex.py`, `a22_create_mails.py` и `a23_mark_compl_in_html.py`.

**Решено 27 июля 2026 года.** После переименований актуальными считаются найденные в snapshot `a13_print_per_aud_conds_tex.py`, `a22_create_mails.py` и `a23_mark_compl_in_html.py`. Старые имена сохраняются только как исторические названия в описании процесса.

### Как сейчас устроены резервные копии?

10. Какая команда или systemd-задача сейчас создаёт резервные копии production SQLite, сколько копий хранится у каждого провайдера и когда в последний раз успешно проверялось восстановление из такой копии?

**Решено для планирования 27 июля 2026 года; proof остаётся открытым.** Внешний cron job создаёт backup и пересылает его на другой физический сервер; копии хранятся долго, но точная команда, количественная retention policy и измеренные RPO/RTO пока не зафиксированы. Запуск из копии фактически работал для Telegram-модуля, который обрабатывает только новые сообщения. Это не доказывает полное восстановление PWA, исторических read models, media/outbox или согласованность SQLite/WAL/SHM, поэтому Phase 11 по-прежнему требует отдельный restore rehearsal.

## Тестовый Telegram-канал

### Где взять канонический ID тестового канала?

11. Где можно получить канонический отрицательный `chat.id` приватного канала `vmsh179devbot channel`, возвращённый Bot API? У тестового бота включён webhook, поэтому `getUpdates` недоступен, а показанный Telegram UI идентификатор `3913815635` метод `getChat` напрямую не принимает. Нужен сам `chat.id` из сохранённого `channel_post` update либо место, где такой update можно безопасно прочитать; вручную добавлять `-100` мы не будем.

**Решено 27 июля 2026 года.** Владелец предоставил канонический test-only `chat.id` `-1003913815635` и подтвердил отправку тестовым ботом. Это разрешённая конфигурация только для приватного test channel, не bot token и не production destination. Harness всё равно обязан выполнить `getChat`/`getChatMember`, закрепить проверенную identity локально и отказаться от любого другого destination; код не выводит `-100` эвристически из произвольного UI ID.

## Перенос истории группы и режима

12. Старый код записывает в `user_changes_log` строку `G` или `O` при каждом вызове команды, даже если группа или режим фактически не изменились. При переносе в `course_enrollment_events` нужно сохранить такие повторные команды как события или схлопнуть последовательные одинаковые значения, оставив только реальные переходы состояния?

**Решено 27 июля 2026 года.** Backfill схлопывает последовательные одинаковые `G`/`O` значения и создаёт `course_enrollment_events` только для реальных переходов состояния. Исходный `user_changes_log` не переписывается, а отчет миграции показывает отдельно число прочитанных строк, отброшенных no-op и созданных событий.

## Перенос истории письменной проверки

13. В старой схеме сообщения `written_tasks_discussions` и результаты `results` связаны только через школьника и задачу: у сообщения нет `result_id`, поэтому для нескольких раундов нельзя достоверно определить, к какому verdict относилось каждое сообщение. Оставить весь старый материал единым непрерывным тредом без искусственно восстановленных связей с раундами проверки?

**Решено 27 июля 2026 года.** Весь legacy-материал переносится в один непрерывный хронологический thread с исходной provenance. Связи message → review round/verdict не угадываются и к «последней проверке» автоматически не приписываются. Новые записи после cutover получают точные связи по новой модели; исторические verdict остаются самостоятельными историческими результатами.

## Доступ к сохранённым данным без сети

14. Если Student или Family уже входили на этом устройстве, можно ли после холодного запуска без сети показать ранее сохранённые условия, новости, результаты и черновики, хотя server не может подтвердить, что сессия ещё действует? Если да, до какого локального срока это разрешено, нужен ли повторный ввод Telegram-токена/пароля и что должно происходить с таким офлайн-доступом после logout на общем устройстве?

**Решено 27 июля 2026 года. Owner-confirmed core:** после хотя бы одного
подтверждённого входа Student/Family может без повторного ввода credential
открыть ранее сохранённый кеш и продолжить черновики. Ранее владелец также
подтвердил, что logout при непустом outbox допустим после предупреждения, даже
если пользователь решит потерять очередь. **Безопасный implementation default:**
кеш account-scoped и показывается в явном состоянии `offline-unverified` не
дольше известного `sessionExpiresAt`; queued mutations ждут сети и повторной
auth-проверки. Явный logout, смена аккаунта или подтверждённая очистка после
предупреждения удаляет кеш, drafts и outbox этого аккаунта, чтобы следующий
пользователь общего устройства их не увидел. Этот default не является открытым
продуктовым блокером.

## Рассылки и отчёт о доставке

15. Какие числа и состояния должен видеть администратор после рассылки через PWA и Telegram: сколько школьников выбрано, сколько исключено настройками или отсутствием доступного канала, сколько отправок начато, успешно доставлено и завершилось ошибкой? Как показывать школьника, которому сообщение доставлено только по одному из выбранных каналов, и как учитывать повторную рассылку после исправления ошибки?

**Решено 27 июля 2026 года. Owner-confirmed core:** предложенные счётчики
доставки подходят; успех только в одном из выбранных каналов допустим, а
получателей полезно показывать в раскрываемых списках. Staff поэтому показывает
по каждому каналу `selected`, `eligible`, `suppressed`, `queued`, `attempted`,
`succeeded`, `failed`, а также общие `deliveredAny`, `deliveredAll` и `partial`.
**Безопасный implementation default:** действие «Повторить ошибки» означает
явную новую попытку только для failed пары `(recipient, channel)`, например
только Telegram конкретного школьника; уже успешная PWA-доставка не дублируется.
Это пояснение закрывает техническую семантику retry и не является новым
продуктовым блокером.

## Решения для production-импорта ученических аккаунтов

16. Какие именно аккаунты нужно включить в первый production-импорт web-входа?
Read-only inventory текущей базы нашёл 10 строк с блокирующими полями или
небезопасной формой Telegram-токена, а также 29 совпадающих login-кандидатов,
затрагивающих 58 школьников. Импортёр намеренно не умеет угадывать решения:
нужен утверждённый локальный файл с исключениями для тестовых/неактивируемых
аккаунтов и с явным уникальным login для каждого участника коллизии. Можно ли
перед production activation показать владельцу сформированный owner-only
detail-report и по нему подготовить этот decision-файл? Идентификаторы, имена,
логины и токены в репозиторий и агрегированный proof не попадут.

**Решено 3 августа 2026 года.** Legacy-inventory не определяет состав первого
набора аккаунтов: учебный год начинается почти с пустой БД, а тестовые строки
будут использованы летом и затем удалены. Staff получает отдельную пакетную
загрузку школьников с полями `surname`, `name`, optional `patronymic`, optional
`birth_date`, optional `school_grade`, `login`, `password`; для школьника
`password` равен его Telegram-токену. Коллизии login не блокируют всю пачку:
импорт предлагает уникальный suffix `-NN` со случайными цифрами и показывает
итоговый login в preview. Синтетические пароли вида `qwerty*` не запрещаются в
test cohort.

По явному решению владельца plaintext-пароли Student и Family сохраняются в v1
для внешней email-рассылки. При этом обычная web-проверка credential продолжает
использовать Argon2 verifier; plaintext не возвращается в browser directory, не
попадает в logs/Sentry/committed proofs и доступен только admin provisioning
workflow и внешнему owner-controlled mail script.

## Шаблоны расписания курса

17. Какую исходную дату должен выбирать администратор при создании группового
занятия, чтобы из шаблона курса рассчитать публикацию условия, подсказки,
решения и дедлайн: дату начала учебной недели, дату публикации условия или дату
самого занятия? Пока реализация использует нейтральное поле «дата начала цикла»
и вычисляет от него отдельные смещения и локальное время каждого события; все
рассчитанные UTC-моменты сохраняются в занятии и позднее не сдвигаются без
preview и подтверждения.

**Решено 3 августа 2026 года.** Основной anchor — локальная дата и время
публикации условия. Курс задаёт шаблон цепочки занятий, группы наследуют его и
могут переопределять отдельные правила. Материализованные timestamps конкретного
`group_lesson` не меняются задним числом без отдельного preview и подтверждения.

## Первый доступ семьи

18. Как при пакетном добавлении школьника создавать и выдавать доступ семье: какой логин использовать, кто задаёт первый пароль и как его передать родителю? Если у семьи в кружке несколько детей, должен ли это быть один общий семейный аккаунт?

**Решено 3 августа 2026 года.** Создание Family-аккаунтов — отдельный второй
batch после школьников. Строка содержит имя родителя, заданные владельцем login
и plaintext password, comma-separated email list и список login детей. Один
Family account связывается со всеми перечисленными детьми. Login/password
Student и Family в v1 рассылаются внешними email-скриптами; Staff не отправляет
эти письма. Каждый ребёнок входит под своим Student account, Family переключает
детей внутри Family PWA. Переключение между несколькими Student accounts в одном
browser считается удобным, но не входит в v1.

## Зачисление нового школьника при Excel-импорте

19. Как Excel-импорт новых школьников должен определять курс и активную группу?
В текущем workbook есть legacy-столбец `level`, но в многокурсовой модели одинаковый
короткий код группы может встречаться в разных курсах. Администратор выбирает один
курс для всего файла, файл содержит отдельные `course`/`group` для каждой строки или
после импорта школьники остаются без зачисления до отдельного действия? Что делать со
строкой без группы: пропускать её с ошибкой или создавать пользователя без доступа к
учебным материалам?

**Решено 3 августа 2026 года.** Создание Student/Family accounts не назначает
курс неявно. Для v1 создаётся один первый курс и отдельная batch-операция с
copy/paste-строками `login, course, allowed_groups`. Та же операция затем
используется отдельно для каждого дополнительного курса. Правило выбора
активной группы при нескольких `allowed_groups` вынесено как единственный
оставшийся вопрос в [`22-development-questions.md`](22-development-questions.md).
