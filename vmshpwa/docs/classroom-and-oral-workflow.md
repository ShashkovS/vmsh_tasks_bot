# Аудитории и устный онлайн-приём

Этот runbook описывает рабочий контур первой версии. Детальные продуктовые
правила находятся в
[плане этапа 7](../dev/development-plan/11-phase-7-oral-and-classrooms.md), а
исполняемые доказательства — в
[сводном отчёте](../../pwa_tests/reports/phase7-consolidated-gates-2026-08-03.md).

## Подготовка очного события

1. Admin открывает `/staff/classrooms`, создаёт очное событие, указывает дату,
   время и выбирает конкретные групповые занятия. Одно событие может объединять
   группы разных курсов; одна аудитория всё равно относится только к одной
   группе. Событие получает читаемый адрес вида `in-person-2026-09-06`; если в
   один день нужны два события, server добавляет короткий числовой суффикс.
   Черновик формы сохраняется в browser localStorage до успешной записи.
2. Вкладка «По группам» показывает наследуемую последнюю подтверждённую схему.
   Пока ничего не изменено, отдельная копия не создаётся. Первая правка создаёт
   event-specific draft; сохранение и подтверждение требуют текущую версию.
3. Вкладка «Школьники» пересчитывает только активных очных участников. Сначала
   сохраняется прежняя допустимая аудитория, остальные попадают в наименее
   заполненную комнату своей группы. Строки без допустимой комнаты остаются в
   «Не распределены / переназначаются» и блокируют подтверждение.
   Заголовок каждой комнаты компактно показывает число школьников и средние
   возраст, класс и силу, поэтому весь план можно быстро проверить без открытия
   отдельных карточек.
4. Локальные single/bulk select сохраняются по аккаунту, событию и base version.
   Reload их восстанавливает. Конфликт версии не перезаписывает черновик: admin
   перечитывает план, сравнивает изменения и повторяет сохранение осознанно.
5. Confirm создаёт неизменяемую версию плана. История школьника продолжает
   показывать прежние подтверждённые назначения. Student и Family сразу видят
   дату и время объявленного события; номер аудитории показывается только из
   подтверждённого актуального плана.

## Рассылка аудиторий

Подтверждение плана никого не уведомляет. Admin отдельно нажимает «Разослать
аудитории», проверяет recipient preview и выбирает PWA и/или Telegram.

- PWA создаёт персональное Student-событие и push delivery; Family только читает
  актуальное назначение и не получает classroom notification.
- Telegram отправляется существующим ботом каждому школьнику в личный диалог,
  а не в канал группы. Browser никогда не получает `chat_id` или bot token.
- Частичная доставка видна по каналам и получателям. Явный retry повторяет
  только failed Telegram-пары и не сбрасывает уже успешную PWA-доставку.
- Любая последующая перестановка снова помечается как неразосланная. Автоматического
  повторного уведомления нет: нужен новый preview и отдельное действие admin.

Если аудитория скрыта после публикации, текущее публичное состояние сразу
становится `reassigning`; прежнее имя и время рассылки не выдаются за актуальные.
Восстановление комнаты само по себе не возвращает старое назначение.

## Устный онлайн-приём

1. Admin настраивает одно или несколько окон конкретного группового занятия.
   Teacher не может менять окна.
2. Online Student видит время и состояние окна. URL и код подключения не входят
   в общий ответ: они возвращаются только по явному tap, только для открытого
   окна, с `Cache-Control: no-store`. Письменная альтернатива остаётся доступна.
3. Teacher с `oral.manage` выбирает Student и выставляет плюсы/минусы по задачам,
   при необходимости добавляя одну внутреннюю реакцию. Незавершённый раунд
   переживает reload; receipt очищает локальный черновик.
4. Результат сохраняется в существующих `zoom_conversation`, `results` и
   `reactions`. Второго журнала устных результатов нет. Повтор с тем же
   idempotency key безопасно возвращает прежний результат.

## Ошибки и восстановление

- `409` на layout/plan/window означает устаревшую версию: локальный draft не
  удаляется, сначала нужен refetch и осознанное сравнение.
- `422` при confirm означает нарушенный инвариант — смешение групп, архивную
  комнату или очного школьника без назначения. Частичный plan не публикуется.
- Сбой NATS/WebSocket после commit не откатывает SQLite. После reconnect клиент
  всегда перечитывает authoritative state.
- Telegram `failed` остаётся видимым до явного retry; отсутствие Telegram
  adapter оставляет строки `queued`, а не изображает успешную доставку.
- PWA-only startup не загружает Telegram/Google credentials и не запускает
  polling.

## Печать и первая миграция

Первая версия не экспортирует и не печатает classroom plan. Подтверждённый Staff
план является источником Student/Family состояния и рассылки, но внешние
`a11`–`a14` и рабочий Excel остаются отдельным источником физической печати до
второй версии. Перед печатью оператор по-прежнему обновляет workbook и запускает
legacy pipeline непосредственно после final readiness sign-off.

Одноразовая команда импорта принимает `IDd`, `Уровень`, `Аудитория`, сначала
показывает hash и blocking diagnostics и применяет только точно просмотренный
preview. Реальный production apply допускается лишь после owner-review; исходный
workbook не становится постоянным API или новым spreadsheet workflow.
