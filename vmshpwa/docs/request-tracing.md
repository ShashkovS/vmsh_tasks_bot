# Диагностика задержек PWA

8 сентября 2026: `helpers/pwa/request_trace.py`, подключение в
`apps/pwa_app.py`, авторизация в `apps/pwa_api/middleware.py`, SQLite в
`db_methods/pwa/connection.py`. Без новых сервисов, БД и миграций.

После обновления backend и перезапуска процесса автоматически включается:

- INFO `pwa_slow_request` для завершившихся API-запросов от 200 мс;
- JSON: request_id, шаблон маршрута (без query и конкретных ID), метод,
  статус, total_ms, агрегированные count/ms этапов;
- `auth`, `db.thread_queue` (ожидание worker), `db.connect` (включая PRAGMA),
  `db.write_lock` (включая busy_timeout и повторы), `db.read`, `db.write`
  (полный callback, не отдельный SQL), `db.commit`;
- INFO `pwa_event_loop_lag` при задержке пробуждения более 100 мс,
  монитор с интервалом 1 секунда на процесс, отменяется при shutdown.

Этапы вложены: auth включает операции БД. Параллельные операции суммируются;
сумма всех этапов не равна времени запроса. Отсутствие db-этапов не исключает
legacy SQL вне PwaConnectionFactory. SQL, его параметры, тела запросов,
заголовки, IP и пользователи не сохраняются. Память на запрос ограничена
агрегатами фиксированных этапов, без списка SQL/spans. После окончания запроса
опоздавшие операции потоков не меняют опубликованную запись.

Сбор после периода обычной нагрузки:

```sh
sudo journalctl -u vmshpwa.service --since "30 minutes ago" --no-pager -o cat | rg 'pwa_slow_request|pwa_event_loop_lag'
```

Не использовать `-p err`: эти записи INFO. Если приложение направляет Python
логи в отдельный файл, искать те же маркеры там. Нужен включённый INFO для
`helpers.pwa.request_trace`; проверить появление строки на известном медленном
запросе. Используется существующее хранение/ротация логов, отдельного архива нет.

Анализ: выбрать обычные школьные GET/POST и review, исключить загрузки/LLM;
сгруппировать по route/method, сравнить стадии и совпадения с loop lag.
Большой thread_queue — очередь executor; write_lock — конкуренция писателей;
db.read/write — исследовать callback и планы SQL; commit/connect — проверить
диск/WAL; большой остаток — точечно инструментировать handler/внешние вызовы.
Трейсы только медленных запросов не годятся для общего p95: использовать
Prometheus вместе с числом запросов. Причина текущих production-задержек пока
не установлена; оптимизация после сбора, не увеличение таймаутов наугад.

Проверки: `pwa_tests/domain/test_request_trace.py` и существующие SQLite fault
tests. Инструментация не меняет транзакции, повторы и правила авторизации.
