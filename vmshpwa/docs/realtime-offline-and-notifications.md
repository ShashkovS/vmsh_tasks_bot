# Realtime, offline и уведомления

## Foreground realtime

Каждое приложение открывает свой WebSocket. Сервер сначала посылает `connected` с текущим cursor. Клиент шлёт `ping`, сервер отвечает `pong`; network backoff имеет jitter и не создаёт reconnect storm. Событие `invalidate` содержит только список ресурсов и причину — после него TanStack Query повторно читает авторитетное состояние.

Cursor помогает обнаружить разрыв в живом соединении, но не является durable event offset. Если клиент сообщает cursor впереди серверного или не может доказать непрерывность, приходит `resync-required`. После reconnect всегда допустим полный refetch версии/состояния из SQLite.

NATS переносит invalidation между процессами. При отсутствии NATS тестовый однопроцессный wrapper вызывает тот же callback. Текущий production baseline — два gunicorn worker, поэтому production требует NATS; увеличение числа workers не меняет протокол.

## Background

Web Push используется только вне foreground и делится на категории: учебный цикл, результат проверки, новый комментарий, новости, организационные сообщения. Пользователь отдельно разрешает категории; отказ браузера не блокирует кабинет. Notification click ведёт на устойчивый deep link внутри audience scope.

Service worker precache-ит shell, KaTeX CSS/fonts и безопасные статические assets. API/auth ответы не попадают в общий Cache Storage. Недавно открытые изображения кешируются примерно на 14 дней с LRU/quota cleanup; общий ориентир локального storage — 10–15 MB. Версия обновляется через явное неблокирующее состояние «доступно обновление» с возможностью применить его после сохранения draft.

На iOS потеря IndexedDB после долгого отсутствия допустима: авторитетные данные находятся на сервере. Student/Family могут не более двух раз мягко предложить установку PWA, но отказ не блокирует работу.

## Offline data

Student и Family имеют отдельные Dexie namespaces по audience и runtime instance. Поддерживаются:

- чтение ранее открытых листков, новостей, подсказок и решений согласно правам на момент cache;
- локальные текстовые drafts;
- подготовленные фотографии и очередь письменной сдачи;
- отображение точного состояния: offline, local draft, queued, uploading, retrying, synced, conflict, failed.

Одна письменная сдача содержит до 10 фотографий. Выбор пользователя обрабатывается worker-ом: orientation, длинная сторона не более 1920 px, WebP и preview. Оригинал не хранится. Если браузер не декодирует HEIC/другой format, aiohttp проксирует временный source в server image service и сохраняет только WebP. Отдельный drag-and-drop reorder не нужен: неверную страницу удаляют и загружают снова в нужном порядке. Клиент не объявляет отправку принятой, пока backend не вернул receipt.

## Outbox и дедлайн

Каждая queued mutation получает UUID idempotency key, `createdAtClient`, timezone offset, payload hash и номер попытки. Сервер записывает `receivedAtServer`, решение дедлайна и audit. Дедлайн — timestamp публикации решений, вводимый в `Europe/Moscow` и хранимый в UTC. Своевременность offline submission определяется по клиентскому времени создания, но подозрительное расхождение часов маркируется для ручного разбора; точный threshold остаётся policy-параметром.

До отдельного подтверждения UX действует безопасное допущение: повтор с тем же ключом и payload hash возвращает тот же результат. Другой payload с тем же ключом получает conflict: исходная операция сохраняется, last-write-wins запрещён, а новая отправка возможна с новым ключом после явного решения пользователя. FIFO действует внутри одной сущности; независимые drafts могут синхронизироваться параллельно. Logout предупреждает о неотправленных данных; после явного подтверждения очередь и drafts этого аккаунта можно удалить.
