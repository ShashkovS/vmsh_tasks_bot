## Sentry: главная нерешённая пользовательская проблема

Sentry снова принимает события. Первый запрос около 16:38 UTC, relative 3h:
VMSHPWA-48 — 965, VMSHPWA-49 — 245, VMSHPWA-4A — 172,
VMSHPWA-4C — 58, VMSHPWA-3S — 56, VMSHPWA-D — 20,
VMSHPWA-4D — 18, VMSHPWA-N — 15, VMSHPWA-3V — 10.
Повторный запрос позже дал другие counts из-за сдвига окна; они не смешаны
с фиксированным Prometheus interval. Event counts — не уникальные пользователи.

[48](https://shashkovs.sentry.io/issues/VMSHPWA-48) и
[49](https://shashkovs.sentry.io/issues/VMSHPWA-49) — query TypeError;
[4A](https://shashkovs.sentry.io/issues/VMSHPWA-4A) — группа ContentNetworkError,
но последний пример тоже TypeError. В примере 49 стек проходит через
invalidateActiveQueries. Это повод проверить refetch/reconnect fan-out,
но не доказательство, что он вызывает все ошибки.

[reportHandledError](../../vmshpwa/packages/app-shell/src/observability.ts)
намеренно заменяет исходную ошибку новым Error с именем типа, скрывая message/cause.
По такому Sentry событию нельзя надёжно различить сбой fetch, ошибку JavaScript,
проблему браузера, сети, CORS или service worker. online=true не подтверждает
доступность сервера. Нужны безопасные bounded tags: шаблон маршрута/семейство query,
класс transport failure, abort/timeout, этап запроса, версия клиента; без ответов
студента, исходных URL и query variables. Дедуплицировать повторные сообщения
одного эпизода: WeakSet сейчас убирает только повтор того же объекта Error.

В примерах соседних событий есть также ожидаемые отказы: D — 401
(authentication_required), N — 422 (test_attempt_hour_limit). Не трактовать
каждое Sentry API failure как HTTP 500 или проблему производительности.
3S пример — service recovery; подтверждает пользовательский эпизод reconnect,
но не объясняет его причину. Последние примеры отдельных issues могут лежать
уже за правой границей фиксированного окна.
