# Логи и производительность ВМШ и TLF с 3 по 8 октября 2026

Уточнение после исходного аудита: причина основных TLF test-input 503
подтверждена историческими metadata задач p-45/46/49; подготовлены изменения
SQL и клиента. [Исправления и проверки](2026-10-08-fixes.md).

Основной инцидент ВМШ произошёл 4 октября: CPU доходил до 100%, обычные
Student API ждали секунды в очереди чтения. Исправление SQL `bdfcf9a2` заметно
сократило задержки, однако короткие очереди повторялись 5–7 октября. Отдельно
4 октября сбои доступа к хранилищу мешали загрузке и выдаче фотографий.
Клиентские ошибки запросов остаются массовыми после восстановления CPU.
TLF значительно быстрее, но имеет отдельный эпизод недоступности test-input.

  [агрегаты](2026-10-08-sentry.json). Дневные counts сверены с общим:

- Доступные journald: [обезличенная сводка](2026-10-08-journal-summary.json).

Counts HTTP приблизительные: `increase` экстраполирует границы и учитывает
сбросы counters. Дневные суммы могут немного отличаться от общего окна.
Latency измеряет backend, объединяет методы и статусы; WebSocket lifetime
исключён. Это не время от клика до отрисовки и не число пользователей.
p95/p99 интерполированы по histogram buckets. Верхняя конечная HTTP корзина
10 с: значение 10 с может означать попадание quantile в открытый хвост,
а не точную задержку 10 с. Ряды с шагом 1/5 минут могут пропускать короткие
события; maxima очередей получены из исходных scrape samples.

Ещё 1 944 события имеют minified title `Ky`; изученный пример
[VMSHPWA-55](https://shashkovs.sentry.io/issues/VMSHPWA-55) — предупреждение
о service recovery, а не самостоятельный crash. Нельзя считать все такие
заголовки одинаковой первопричиной без анализа отдельных событий.
TypeError сохраняются после CPU correction: 2 835 / 2 253 / 2 132
за 5 / 6 / 7 октября. Повторные попытки одного эпизода дают много событий.

[reportHandledError](../../vmshpwa/packages/app-shell/src/observability.ts)
создаёт новый Error, сохраняя тип, HTTP code и bounded context, но удаляет
исходные message/cause. Поэтому [VMSHPWA-52](https://shashkovs.sentry.io/issues/VMSHPWA-52)
не позволяет установить, что именно вызвало TypeError: сеть, CORS,
JavaScript, service worker или другой этап. `online=true` не подтверждает
доступность backend. Среди API failures отдельно видны 577
`oral_window_not_found`, 527 `authentication_required`, 299 `session_revoked`,
95 `test_attempt_hour_limit`. Доменный отказ нельзя считать серверным HTTP 500.

Данные Sentry неполные: hourly outcomes возвращают около **31 758 отброшенных
сообщений**, включая 11 574 `ratelimit_backoff`, 1 938 `spike_protection`,
1 301 `network_error` и 16 945 `event_processor`.
Последняя часовая корзина до 08:00 UTC частичная; outcomes и stored event
counts могут немного расходиться по времени доставки. `event_processor`
может означать намеренную фильтрацию. Отброшенные сообщения нельзя прибавлять
к сохранённым как уникальные пользовательские сбои, но backoff/spike protection
делают график принятых событий ненадёжным показателем истинного пика.

В проекте Sentry `vmsh179bot` за окно 390 событий: 347 disconnect во время
PWA WebSocket prepare, 42 disconnect при чтении JSON push-subscription и
одна SQLite write-lock failure фоновой push delivery 6 октября 11:41:35 UTC.
Это PWA, несмотря на название проекта.
На ВМШ все ≈40 HTTP 500 в Prometheus — push-subscriptions; на TLF таких ≈15.
[Исследованный stacktrace](https://shashkovs.sentry.io/issues/VMSH179BOT-2W)
показывает `ConnectionResetError` во время `request.read`,
а [write-lock sample](https://shashkovs.sentry.io/issues/VMSH179BOT-31)
— исчерпание четырёх попыток `BEGIN IMMEDIATE`. Их counts не сопоставлены
с каждым HTTP один к одному. Доказательств потери ответов из этих групп нет.

## Старое сообщение школьника

Предоставленный скриншот от **26 сентября 20:53** сообщает об ошибке отправки
с меткой **`client:UnknownError`**. Его время не содержит timezone;
он находится вне основного окна аудита.

[Test outbox](../../vmshpwa/packages/offline/src/test-answer-outbox.ts) и
[written outbox](../../vmshpwa/packages/offline/src/written-submission-outbox.ts)
формируют `client:${error.name}` для Error. Это отличается от запасной
метки `client:unknown` и от структурированного `api:status:code:request=…`.
Одна метка не показывает HTTP status, факт принятия ответа или стадию сбоя.

Рабочая гипотеза — ошибка локального хранилища/outbox: приложение использует
[Dexie поверх IndexedDB](../../vmshpwa/packages/offline/src/database.ts), а
[Dexie.UnknownError](https://dexie.org/docs/DexieErrors/Dexie.UnknownError)
означает сбой нижележащей реализации базы в браузере. Это не доказанная
причина конкретного случая. В актуальном transport сетевые сбои обычно
превращаются в отдельные `TestSubmissionNetworkError` /
`WrittenSubmissionNetworkError`; версия клиента школьника неизвестна.
Запрос Sentry за UTC-день 26 сентября по `UnknownError` не нашёл события;
это не опровергает жалобу и не подтверждает потерю ответа.

Для повторного случая нужна безопасная диагностика стадии
`enqueue / claim / request / receipt / persist`, вида локальной операции,
browser/version, имени исключения и bounded requestId, без текста ответа и
фотографий. До подтверждения серверной квитанции нельзя советовать удалять
данные приложения: в outbox может оставаться единственная копия ответа.

## TLF и доступность

TLF: **162 883 HTTP**, около **38 >1 с, 0,023%**; после CPU correction
p95 задач 35 мс, контента 40 мс, auth/me 15 мс. Read queue после correction
не выше 5 у одного worker. Средний CPU shared host 3,35%, RAM available
не ниже 3,38 ГиБ. Отдельные минутные CPU peaks до 98% и disk busy до 72%
не доказывают загрузку именно PWA: на сервере работают другие приложения.

При этом примерно **1 111 ответов 503 на test-input** пришлись на час
**4 октября 10:00–11:00 UTC**. Это функциональная недоступность при низкой
обычной API latency. [Submission handler](../../apps/pwa_api/submission_routes.py)
переводит repository/configuration exceptions в `test_submissions_unavailable`;
первопричина этого исторического эпизода по доступному journal не установлена.
Быстрый ответ с ошибкой не означает исправную отправку.

ВМШ aiohttp scrape: семь неудачных samples из ≈31 220; TLF: 21 из ≈31 218.
Это короткие эпизоды, частично рядом с выпусками, а не точная длительность
пользовательского простоя. На TLF blackbox `probe_success` главной страницы
равен 1 в имеющихся samples, но probes покрывают только последние ≈47 часов
и не проверяют авторизованную отправку. Prometheus rule groups пусты на обоих
серверах; наличие независимых Grafana alerts этим запросом не проверяется.

Исторический journal ВМШ закрыт sudo allowlist; доступны последние 100 строк.
Полученный PWA-фрагмент 8 октября 07:04:39–07:09:35 частично выходит за окно:
86 DB diagnostic records, преимущественно background push/publication,
202–333 мс; отдельные обычные reads ждут admission почти всё время запроса.
Этот фрагмент подтверждает механизм текущего ожидания, но не объясняет
владельца слота в пиках 6–7 октября. Telegram-фрагмент из 100 строк
4 октября 11:57 — 8 октября 06:56 содержит restart/shutdown и служебные
warnings без traceback/уровня ERROR; это не полная история Telegram.
TLF journal вернул 116 строк только с 7 октября 03:59:05:
три `ConnectionResetError` и восемь медленных успешных uploads,
в основном conversion. Полный период журналами не покрыт.

В [logging configuration](../../helpers/config.py) используется
`%Y-%d-%m`: например, `2026-08-10` в application asctime здесь означает
8 октября. Хронология установлена по journald/Sentry timestamps, не по
похожему на ISO тексту asctime.

## Приоритеты следующей работы

1. Разобрать короткие read bursts 6–7 октября с владельцами слотов и
   breakdown SQL/admission. Проверить планы долгих Staff statistics,
   refetch/invalidation и background write jobs; снять профиль на копии
   production данных. Не подменять эту диагностику увеличением workers.
2. Для media сохранить bounded transport failure classification и stage
   timings на GET/PUT, проверить эпизод 4 октября по доступным серверным
   журналам/метрикам провайдера. Отдельно benchmark конвертации: после
   восстановления хранилища она остаётся главным постоянным этапом upload.
3. Установить repository/configuration exception, вызвавший TLF test-input
   503, и добавить безопасную диагностику такой обработанной ошибки;
   readiness главной страницы не проверяет этот сценарий.
4. Улучшить классификацию клиентских query/submit/storage failures,
   подавление ожидаемых отмен и дедупликацию одного эпизода. Для старого
   `client:UnknownError` в первую очередь нужны стадия и браузер,
   не предположение об отсутствии интернета.
5. Разобрать disconnect в push-subscription/WebSocket и редкую write-lock
   failure, затем активировать согласованные latency/queue/error alerts.

Аудит выполнен read-only: код приложения, конфигурация серверов, учебные
данные и Sentry issue state не изменялись. В репозитории сохранены только
отчёт, агрегаты, воспроизводимые запросы и status. Коммита/deploy нет.
