## 1. Загрузка фотографий — устойчиво медленный пользовательский путь

`POST /student/api/v1/thread-entries/{entry_public_id}/attachments`:
**662 requests, mean 1 914 мс, p95 ≈4 439 мс, 520 (78,5%) >1 с**.
Это наиболее устойчивый секундный маршрут. Его p95 — главный кандидат на
длинную линию на присланном графике; без легенды цвет нельзя сопоставить точно.

[create_written_attachment](../../apps/pwa_api/written_submission_routes.py)
ждёт multipart, затем [WrittenAttachmentService](../../helpers/pwa/written_attachments.py)
последовательно выполняет подготовку в БД, конверсию, storage.put и фиксацию.
[Конвертер](../../helpers/pwa/content/assets.py) использует ImageMagick → PNG →
cwebp. Здесь несколько возможных источников задержки; их доли не измерены.

Что делать:
1. Добавить stage timings multipart/read, normalization, webp, storage.put,
   DB prepare/complete; собирать размер входа и результата без содержимого.
2. По результатам сравнить один проход конверсии с текущими двумя и уменьшение
   фото на клиенте, сохранив серверную валидацию и требования качества.
3. Ограничить конкурентные конверсии; при необходимости отдельный worker и
   честный progress UI. Фоновая конверсия требует изменения контракта и
   идемпотентности, её нельзя просто запустить fire-and-forget.

## 2. Очередь reader — подтверждённый источник эпизодических задержек

За 48 часов примерно 1 208 287 read admission operations:
mean hold **1,95 мс**, p95 hold **9,77 мс**, mean wait **12,61 мс**,
p95 wait **34,51 мс**. Максимальная наблюдавшаяся очередь **156** у одного
worker и **90** у второго; максимумы не обязательно одновременны.
В минутной выборке максимум пятиминутного p95 read wait ≈**2,10 с**
26.09 09:01 UTC.

Обычные API в целом быстрые:

| Маршрут | Requests | Mean | p95 | >1 с |
| --- | ---: | ---: | ---: | ---: |
| auth/me | 36 960 | 16,6 мс | 33,2 мс | 141 |
| список задач занятия | 39 296 | 90,6 мс | 202,4 мс | 435 |
| опубликованный материал | 37 374 | 88,1 мс | 198,9 мс | 433 |
| test-input | 13 518 | 52,8 мс | 99,2 мс | 95 |

При этом локальные всплески p95 content достигали 8,25 с, problems 7,70 с
26.09 09:01 UTC. 25.09 около 21:34 UTC также есть совместный всплеск API и CPU.
Исторического журнала недостаточно, чтобы назвать владельца read slot в эти моменты.

В свежем журнале 27.09 09:37:03 UTC test-input: total **651,30 мс**,
admission **635,99 мс**, db.read **1,37 мс**. У content: total **754,46 мс**,
admission **736,58 мс**, db.read **1,98 мс**. По 55 slow requests первого
фрагмента: суммарно 23 888 мс, из них 21 049 мс (88,1%) admission.
`auth` и `db.admission_queue.read` вложены в другие стадии — их нельзя суммировать.

[connection.py](../../db_methods/pwa/connection.py) имеет один постоянный
reader на worker; запросы делают по 3–4 последовательных захода. В
[realtime.tsx](../../vmshpwa/packages/app-shell/src/realtime.tsx) reconnect
запускает refetch всех активных queries. Это правдоподобный усилитель очереди
после deployment. Backoff уже содержит jitter, но сам пакет refetch остаётся
параллельным. Причина исторических всплесков этим не доказана.

Порядок действий: сохранить полный журнал нагруженного интервала с holding/
released/admitted, устранить длинного владельца либо пакетный fan-out;
сократить повторные чтения в пределах одного запроса; сгладить refetch после
reconnect. Затем сравнить 1 и 2 persistent readers на worker на изолированной
копии. Не кешировать права доступа между запросами без политики инвалидирования.
Продолжение ранее принятого решения: [SQLite admission](../../vmshpwa/docs/sqlite-admission-performance.md).

## 5. Остальные улучшения

- **Выдача фото:** staff media — 3 402 запроса, mean 246 мс, p95 500 мс;
  student — 1 644, mean 157 мс, p95 341 мс. `_attachment_media_response` в
  [written_submission_routes.py](../../apps/pwa_api/written_submission_routes.py)
  на каждый запрос читает весь object и проверяет SHA256; выставляет ETag,
  но самостоятельно не обрабатывает If-None-Match. Кандидат: после актуальной
  авторизации вернуть 304, использовать приватный cache проверенного immutable
  object и thumbnails. Нельзя открывать приватные фото публичным CDN.
- **Фоновые DB операции:** write admissions ≈308 671 за 48 ч; ночью типичный
  rate ≈1,58/с даже при низком трафике. Это допуски к write callback, не число
  изменённых строк или fsync. В [pwa_app.py](../../apps/pwa_app.py) scheduler и
  push loops запускаются каждым worker с интервалом 5 с. В свежем журнале
  oral notification callback держал write slot 2,67 с, push prepare — 1,90 с.
  Они попали в deployment burst, это не типичные длительности. Проверить
  no-op polling, batch и единственного владельца scheduler с lease/failover.
  Сеть push уже выполняется вне write callback: переносить её повторно не нужно.
- **Авторизация:** ≈24 111 ответов 401 (8,04%), auth/me — 9 631 из 36 960.
  Возможны нормальные истечения access token и анонимные визиты; это не
  доказанный auth bug. Проверить single-flight refresh, запуск queries только
  после auth-ready и лишние retries. Снижать лишние запросы без ослабления auth.
- **Редкие тяжёлые операции:** recheck-test-attempts — всего 2 HTTP запроса
  (GET/POST объединены), mean 10,57 с. Недостаточно для устойчивого p95;
  проверить раздельно preview/recheck и необходимость job/progress.
- **Staff statistics:** 359 requests, mean 467 мс, p95 931 мс. Analytics gate
  изолирован; его p95 hold 760 мс. Это отдельная задача SQL-оптимизации, ниже
  приоритетом, чем uploads и интерактивные очереди.

## Как читать присланные графики и что изменить в мониторинге

HTTP buckets: 0,5 / 1 / 2,5 / 5 / 10 с. При малом числе запросов p95,
интерполированный внутри bucket, естественно даёт 0,475 / 0,975 / 2,425 /
4,875 с. Ступени не доказывают фиксированный sleep или timeout. Это свойство
[гистограмм Prometheus](https://prometheus.io/docs/practices/histograms/).
Но 520 uploads >1 с — реальное подтверждение медленного пути независимо от p95.

Нужны панели по классу операций: interactive/upload/report; requests count
рядом с quantiles; p99 и доля >0,5/>1/>5 с; отдельно 2xx/5xx и method;
очереди по worker, loop lag и release annotations. Алерт на маршрут, а не
только общий 5xx. При добавлении bucket boundaries учитывать период перехода
между старой и новой схемой; нельзя смешать разные схемы без оговорки.

## Принятое изменение: не пересчитывать SHA256 при выдаче фото

27 сентября пользователь решил отказаться от повторной проверки хеша на каждом
чтении. В `_attachment_media_response` из
[written_submission_routes.py](../../apps/pwa_api/written_submission_routes.py)
удалён пересчёт SHA256 тела для student/family/staff. Проверки доступа и дешёвые
проверки размера/type сохранены. Хеш проверяется при загрузке и берётся из
метаданных для ETag без пересчёта. S3 GET пока остаётся: удаление хеширования
само по себе не устраняет сетевую задержку и не доказывает ускорение на 246 мс.
