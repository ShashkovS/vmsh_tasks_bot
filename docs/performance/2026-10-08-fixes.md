## Короткие задержки

Подтверждена стоимость повторной пустой push candidate selection внутри
writer callback: 164–190 мс на одной временной копии production DB,
хотя уведомлений к отправке нет. В live journal callbacks push занимают
200–300 мс и задерживают следующий writer. Migration
[0116](../../migrations/0116.notification_push_candidate_index.py) добавляет
частичный индекс unread events по account/due/id/category для
[list_due_candidates](../../db_methods/pwa/notification_deliveries.py).
После индекса неизменённый SQL на той же копии: 32–36 мс, строки совпадают,
605k → 384k VM steps. Источник открыт mode=ro; индекс создан только в
удаляемой temporary copy. Это измерение одной выборки, а не обещание нового
production p95. Переписывание SQL и scoped result-group projection не дали
устойчивого выигрыша и не применяются.

[Regression/migration rehearsal](../../pwa_tests/integration/test_push_candidate_index.py)
проверяет реальный SQL, rollback/apply, сохранность rows, integrity и bounded
VM steps с 5000 future/read events. Остальные push сценарии остаются в
[test_phase8_push_delivery.py](../../pwa_tests/integration/test_phase8_push_delivery.py).

## TLF test-input 503

Из nginx за 4 октября: 1120 HTTP503, из них p-45 — 834, p-46 — 263,
p-49 — 17 (1114/1120). Prometheus ≈1111 — иной способ подсчёта/границы.
Первый/последний nginx 503: 07:49:16/10:40:23 UTC. Резервная копия
09:38 UTC содержит у всех трёх SELECT_ONE (98), answerValidation=null,
ноль видимых вариантов. В копии 11:56 UTC тип уже STRING (99).
[get_test_answer_input](../../db_methods/pwa/submissions.py) в таком случае
выбрасывает SubmissionConfigurationError; HTTP adapter превращает его в 503.
На 5–8 октября в доступных nginx logs test-input 5xx отсутствуют: 365/347/217/50
успешных загрузок по дням, отдельно 401 и один 499. Текущие 32 published test
revisions проверены независимо от eligibility: пустых SELECT_ONE нет.
Первые агрегатные проверки 25/32 eligible revisions не покрыли эти задачи;
валидность того subset не была доказательством корректности отказавших форм.

Общее правило [TestProblemAnswerConfig.input_options](../../models/pwa/submissions.py)
используется при загрузке формы, сохранении reviewed metadata через
[ProblemMetadataDraft.as_revision_draft](../../models/pwa/content.py) и проверке включённых (answer_type != NULL) inputs в
[publication readiness](../../db_methods/pwa/content.py). Пустой SELECT_ONE
не подтверждается и не допускается через publish/schedule/rollback HTTP gate.
Исторический draft остаётся читаемым и исправляемым; тип ответа автоматически
не заменяется, grading и попытки не меняются. Ошибка save остаётся 422
content_validation_failed; publication gate сообщает invalidTestInputs в details.
[Regression](../../pwa_tests/integration/test_test_input_publication_guard.py)
проверяет отказ save, неготовность повреждённого reviewed snapshot и явное
исправление типа. [HTTP proof](../../pwa_tests/integration/test_content_http_api.py)
проверяет отклонение плохой grid без изменения состояния.

## Клиент

[ServiceTransportError](../../vmshpwa/packages/contracts/src/service-availability.ts)
разделяет offline, recovering, deadline и network. Offline/cache/outbox границы
сохранены, неоднозначные writes не получают автоматический replay. Исходный
cause остаётся локальным, в Sentry попадают только разрешённые категории.
[retryQuery/queryFamily](../../vmshpwa/packages/app-shell/src/query-errors.ts)
не повторяют ожидаемые offline/recovery reads, AbortError и HTTP4xx. Настоящие
network/deadline/programming failures сохраняют одну повторную попытку.
[reportHandledError](../../vmshpwa/packages/app-shell/src/observability.ts)
отсеивает только подтверждённые offline/recovering query failures.
Необъяснённые AbortError сохраняются: это может быть timeout/IndexedDB,
а не пользовательская отмена. Ошибки отправки не скрываются.
Реальные query failures получают безопасную family и transport_kind без
полных query keys, сообщений, URL, answers или causes.

[resyncActiveQueries](../../vmshpwa/packages/app-shell/src/query-resync.ts)
объединяет пересекающиеся online/WS/service-ready waves, ограничивает concurrency четырьмя
active queries и не восстанавливает cache, очищенный при logout. Auth идёт
первым, более старая authority проверка отменяется ровно в рамках новой wave.
[ServiceAvailabilityBanner](../../vmshpwa/packages/app-shell/src/service-availability.tsx)
использует ту же wave вместо массового invalidate/refetch. Стандартный
Query reconnect refetch отключён; auth сохраняет свой opt-in до входа.
[RealtimeProvider](../../vmshpwa/packages/app-shell/src/realtime.tsx) ждёт её
перед очередным resource invalidation, чтобы не терять изменения во время
resync. [Поведенческие проверки](../../vmshpwa/packages/app-shell/src/query-resync.test.ts),
[service-ready regression](../../vmshpwa/packages/app-shell/src/service-resync.test.tsx),
[authority regression](../../vmshpwa/packages/app-shell/src/realtime-provider.test.tsx),
[classification/privacy](../../vmshpwa/packages/app-shell/src/query-errors.test.ts),
[transport](../../vmshpwa/packages/contracts/src/service-availability.test.ts).

## Refresh при перезагрузке

Реальный Chromium E2E обнаружил потерю сессии при private reload. Из trace
выведены только method/path/status и error code: старый POST /auth/refresh
завершён status=-1 при reload, следующий refresh получает session_revoked.
Ответ вращающего single-use cookie запроса был потерян между документами.
[AuthClient.#send](../../vmshpwa/packages/app-shell/src/auth-client.ts)
теперь ставит keepalive только на /auth/refresh; Web Locks, поколения refresh,
проверка authority и запрет повторной ротации остаются прежними.
[Auth client unit](../../vmshpwa/packages/app-shell/src/auth-client.test.ts): 16 PASS.
[Private reload acceptance](../../vmshpwa/e2e/authentication.spec.ts):
3 повтора × Chromium/WebKit/Firefox = 9 PASS через lock-aware runner.
Production не изменён.

Logout regression: Firefox получил POST logout 204 и auth/me 401, но следующий
`page.evaluate(fetch)` в тесте отменён при переходе/reload документа.
В [authentication.spec.ts](../../vmshpwa/e2e/authentication.spec.ts) только
проверка отказа после logout использует `context.request` с тем же cookie jar.
Проверки 401, очистки cookies, ухода на login и durable logout сохранены.
Product logout, session policy и acceptance assertions не ослабляются.
