## Что делает цепочка

### a11: люди, аудитории и навигационные списки

`parse_xls_conduit` читает `Итог` с шестой строки: A фамилия, B имя, C token/ID,
D класс, F скрыть, G уровень, L аудитория; дополнительно H и K, но их подписи
в примере Excel уже отличаются от старых имён в конфигурации. Проверяет ID
и отсутствие смешанных уровней в комнате. Затем a11 отбрасывает скрытых,
строки без аудитории или уровня и применяет при необходимости разделение
большой комнаты на технические подгруппы.

- `spisok-*`: строки для будущих кондуитов; фамилия, имя, класс, пустые строки
  до минимума 27, разделители каждые три строки, повторная шапка после 9 и 18.
  Пустая `phantom`-строка задаёт ширину колонки, это не ученик.
- Code128: номер занятия, аудитория, упорядоченные внутренние ID из локальной
  SQLite по Excel token и контрольная сумма. Порядок должен совпадать с таблицей.
- Дверные списки: крупный номер комнаты, дата, ФИ; до двух колонок на странице,
  продолжение на новых страницах. При большом составе исчезает нижняя памятка.
- Общий список: четыре колонки «ФИ → аудитория», длинные имена сокращаются,
  ё при сортировке считается е; возможны замены технических номеров на физические.
  Обычно A3; для малого списка предусмотрен A4 landscape.
- `zstats.pickle`: промежуточные количества по уровню/аудитории и время расчёта.

### a12: печатные варианты учебного материала и пустые кондуиты

Работает с исходниками условий `usl-NN-{n,p,x}.tex`, готовыми PDF, стилем и рисунками.
Удаляет часть полиграфических команд, объявлений и повторов; из структуры задач
и пунктов строит колонки кондуита. Размер ячеек зависит от количества задач/людей.
Создаёт PDF с поаудиторными пустыми кондуитами и запасным пустым списком.

Учительский вариант — компактные **условия текущего занятия**, с водяным знаком
«Учитель», а не обязательный комплект текущих решений. Скрипт подбирает масштаб,
стараясь уместить его на одну страницу. Заготовки решений, старый кондуит
и отдельная сборка устных решений присутствуют в коде, но вызовы отключены.
Готовый ученический PDF берётся из исходной папки; a14 использует именно его.

### a13: прошлые результаты для нынешней аудитории

Берёт состав аудитории из текущего Excel, имена/класс/группу из SQLite,
задачи предыдущего номера (`cur_les - 1`) и результаты через синонимы задач.
Это **нынешние ученики комнаты × прошлые задачи**, не историческая рассадка.
Группу выбирает большинством среди найденных учеников комнаты.

Оценки переводятся в `+`, `±`, `+/2`, `∓`, `−` по порогам
0.95 / 0.7 / 0.4 / 0.2. Шапка содержит номера, пункты и проценты; повторяется снизу.
Пустота отличается от минуса: нет результата против имеющегося отрицательного.
В старом коде процент считается по наличию символа `+` в TeX-строке:
полный плюс и половинка учитываются, `±` и `∓` — нет. «Посещение» выводится
при наличии полного плюса или минуса; это косвенная эвристика, не журнал прихода.

### a14: тираж и сборка пачек

Для каждой аудитории в итоговой сборке:

1. Односторонне — одна таблица прошлых результатов; при отсутствии файла
   прошлых результатов вместо неё текущий кондуит с пометкой «Основной».
2. Двусторонне — **три** копии пары «пустой текущий кондуит / учительские условия».
3. Каждому ученику — экземпляр текущих условий. Одна страница идёт в одностороннюю
   пачку, две — в двустороннюю, более двух скрипт не принимает.
4. На аудиторию — один комплект решений прошлого занятия, если он существует;
   при нечётном числе страниц добавляется пустой оборот.

Образец это подтверждает: 36 учительских листов + 34 листа прошлых решений =
70 двусторонних листов; отдельно 192 односторонних листа, 12 дверных и один A3.
Основные общие пачки уже содержат повторы: печатаются по **одной копии файла**.
Есть дополнительные PDF по уровням, где предполагаемый тираж написан в имени;
семантика копирования у них другая. Поаудиторное сохранение предусмотрено,
но закомментировано.

## Какие legacy-детали нельзя автоматически считать требованиями

- В настройках указаны 4 учительских кондуита и 16 условий на аудиторию,
  но общая сборка реально использует 3 учительских пары и число учеников.
- Код a12 берёт статистику колонок до её обновления в конце запуска:
  не следует переносить зависимость от старого `pickle`.
- a12 перечисляет файлы без явной сортировки, a14 считает их страницы по
  отсортированным аудиториям. Новый сборщик должен связывать страницу с ID
  аудитории явно, не угадывать по позиции файла.
- a13 не повторяет весь фильтр a11 и не применяет его `change_split_auds`.
  Состав разных документов может разойтись на иных данных.
- Код рассчитан на одну страницу результата на комнату и очень узкие таблицы;
  переполнение может нарушить сопоставление страниц.
- Общий список рассчитан максимум на два листа; автоматическое уменьшение
  шрифта нельзя продолжать неограниченно.
- Четырёхзначное кодирование штрихкода обрезает большие числа. Замена ID или
  формата требует согласования с декодером; наличие QR-команд в стиле не значит,
  что сейчас используется QR. Сам декодер Code128 здесь не найден.
- a18 показывает зависимость распознавания от структуры таблицы и порядка
  строк. Проверка реальных сканов необходима, если этот процесс остаётся.
- Условия в комплекте могут содержать служебные/скрытые материалы внутри
  LaTeX-исходника. Печатный профиль ученика должен явно выбирать только условия.

## Возможности рендеринга и варианты

Уже есть [Student print CSS](../../vmshpwa/apps/student/src/student-worksheet-print.css)
и [контракт](../../vmshpwa/docs/worksheet-print.md): печать показанных занятий,
раскрытых подсказок/решений, A4, 11 pt. Это полезная основа, но её текущая
семантика не подходит для массового комплекта ученикам без отдельного профиля.

Также есть [PdfDerivativeRenderer](../../helpers/pwa/content/pdf.py),
[PdfPersistenceService](../../helpers/pwa/content/pdf_service.py) и защищённая
выдача сохранённого PDF в [content routes](../../apps/pwa_api/content_routes.py).
Это заготовки для ограниченного воспроизводимого pdflatex и хранения артефактов.
В просмотренном runtime-коде не найден вызов этих двух классов; нельзя считать
генерацию PDF уже подключённой. Renderer пишет source/driver, но не материализует
пакет `newlistok.sty` и всех рисунков. Их перенос и реальная компиляция требуют
отдельной проверки. Он также не является сборщиком печатных пачек.

| Вариант | Плюсы | Цена и ограничения |
| --- | --- | --- |
| A. Весь комплект через LaTeX | Максимально близкая плотная вёрстка, проще сохранить кондуит | Подготовка шаблонов, стиля, шрифтов и рисунков; TeX остаётся частью runtime |
| B. Весь комплект HTML/CSS → браузер/PDF | Общие web-компоненты, простые правки списков и таблиц | Новая пагинация математики, риск роста числа страниц; точную старую геометрию надо доказывать |
| C. Смешанный | LaTeX/PDF для условий и решений; отдельный renderer таблиц/списков; общий сборщик | Два вида renderer, зато можно переходить постепенно и сохранить сложную вёрстку |

Предварительная рекомендация — C. Если распознавание обязательно, текущий
кондуит на первом шаге тоже оставить в TeX; браузерные списки можно добавлять
независимо. Если точная полиграфия не нужна, B становится проще для развития.

Для B/C серверный Chromium может печатать отдельную HTML-страницу с print CSS
в PDF с явным размером листа — [Playwright page.pdf](https://playwright.dev/docs/api/class-page#page-pdf).
Печатная страница должна полностью загрузить шрифты, формулы и изображения,
а не зависеть от того, что пользователь раскрыл или прокрутил на экране.
Сборку повторов и страниц можно делать отдельно, например средствами
[pypdf](https://pypdf.readthedocs.io/en/latest/user/merging-pdfs.html).
Ни один новый renderer/пакет в этой работе не установлен и не испытан.

## Предлагаемый процесс и последовательность реализации

Admin открывает очное событие → «Печать» → выбирает аудитории и состав бумаг →
видит количество учеников, резерв, экземпляры и листы → смотрит образцы →
получает общий список, дверные списки, одностороннюю и двустороннюю пачки.
Нужна также выборочная перепечатка комнаты/документа.
Для полного тиража предпочтительны готовые PDF; HTML удобен для preview
и разовой печати отдельных списков. Прямую отправку на принтер не предполагаем.

1. После ответов владельца зафиксировать состав комплекта и правила результатов.
2. Собрать единый снимок: событие, версия confirmed plan, подписи/порядок учеников,
   версии текущих/прошлых материалов, порядок задач, результаты/посещение,
   время среза, тиражи, версии шаблонов. Не держать DB-транзакцию во время рендера.
3. Подготовить один полный комплект аудитории; проверить плотность, формулы,
   подпункты, запасные строки и при необходимости распознавание реального скана.
4. Добавить списки и сборщик тиража. Связь документа и аудитории хранить явно.
   Каждый новый документ в duplex начинается с лицевой стороны; выравнивать
   каждый блок, а не только последний файл решений. A3 держать отдельным файлом.
5. Добавить admin UI, фоновую генерацию, скачивание, ошибки, повтор и выборочную
   перепечатку. Различать «повторить прежний комплект» и «собрать обновлённый».
6. Проверить полную пачку: состав и количество копий, отсутствие утечки решений
   в ученические условия, смену групп, несколько курсов, длинные имена,
   большие аудитории/таблицы, пустые результаты, отсутствующие прошлые решения,
   нечётную пагинацию. Старые реальные ФИ не превращать в committed fixtures.

Изменение плана или результатов после формирования не должно молча менять
сохранённый PDF. UI показывает, что данные обновились. Генерация не выполняет
публикацию учебных материалов и не отправляет уведомления об аудиториях.
Печатные списки/результаты выдаются через admin-authorized endpoint, не через
общедоступный URL учебного media. Backend остаётся существующим aiohttp/Python.
